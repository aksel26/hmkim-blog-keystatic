# Product

<!-- impeccable:product-schema 1 -->

이 문서는 `apps/agent-web`만 다룬다. 공개 블로그(`apps/blog`)의 요구사항은 `docs/PRD.md`에 있다.
2026-09-21 사용자 인터뷰와 저장소 코드로 확인한 사실만 적었다. 정해지지 않은 것은 "미정"으로 표시했다.

## Platform

web

## Users

**주 사용자는 저장소 주인 한 사람이다.** 프론트엔드 개발자이고, 자기 블로그(HM Blog)에 올릴 글을 이 도구로 만들어 내보낸다.

- 쓰는 방식: 주제를 넣어 생성을 시작해 두고 다른 일을 한다. 나중에 데스크톱으로 돌아와 결과를 검토하고 승인한다. 한자리에서 끝까지 지켜보는 도구가 아니다.
- 돌아왔을 때 하는 일: 내 결정을 기다리는 작업을 찾는다. 초안을 읽는다. 승인, 수정 요청, 재작성, 보류 중 하나를 고른다. 마지막으로 PR 생성을 승인한다.

**두 번째 청중은 면접관이다.** 주인이 이직 과정에서 화면 캡처나 라이브 데모로 보여 준다. 짧은 시간 안에 이 도구가 무엇을 하고 어떤 판단으로 설계됐는지 읽어 낸다.

다른 사람이 직접 쓰도록 여는 계획은 현재 없다.

## Product Purpose

AI가 블로그 글 초안을 만들고, 사람이 검토해 PR로 내보내는 과정을 운영한다.

잘 되고 있는지는 네 가지로 판단한다 (사용자 확인).

1. 파이프라인으로 실제 나간 글이 꾸준히 늘어난다.
2. 초안을 읽고 고쳐 승인하기까지 걸리는 시간이 준다.
3. 반려 없이 통과하는 초안이 늘어난다.
4. 면접관이 봤을 때 사람 개입 설계와 운영 수치가 드러난다.

## Positioning

**애매한 신호는 자동으로 처리하지 않고 사람에게 넘긴다.** 글을 자동 발행하지 않는다.

- 사람이 개입하는 지점이 두 곳이다. 사용자 검토에서 내용을 판단하고, PR 생성 승인에서 발행을 결정한다. 머지는 GitHub에서 사람이 한다.
- 형식 검증은 LLM 없이 정해진 규칙으로 한다. 검증이 실패한 글은 승인해도 PR을 만들지 않는다.
- 반려하면 리서치는 다시 하지 않고, 검토한 최종본에 피드백만 반영해 다시 돈다. 반려 상한은 3회다.

근거와 세부 내용은 `docs/ARCHITECTURE.md`에 있다.

## Operating Context

- 실행: 로컬에서 `pnpm dev:agent-web` (port 3001). **배포 여부와 위치는 미정이다.** `vercel.json`은 비어 있다.
- 생성은 서버에서 백그라운드로 돌고, 화면은 진행 상황을 실시간으로 받아 보여 준다.
- 데이터는 Supabase에 있다: 작업(`jobs`), 진행 로그(`progress_logs`), 뉴스레터 구독자, 이메일 템플릿.
- 발행 경로: GitHub에 `post/{날짜}-{slug}` 브랜치를 만들고 PR을 올린다.
- 모델은 Gemini 3.6 Flash 하나다. 무료 티어 한도 안에서 운영한다.
- 화면 언어는 한국어다.

## Capabilities and Constraints

**화면**

| 경로 | 하는 일 |
|---|---|
| `/` | 작업 수, 완료, 검토 대기, 성공률. 최근 작업 |
| `/generate` | 카테고리(기술/라이프), 주제, 템플릿, 말투, 타겟 독자를 넣어 생성 시작 |
| `/jobs`, `/jobs/[id]` | 작업 목록과 상세. 9단계 진행 상황, 콘텐츠 미리보기와 직접 편집, 메타데이터, SEO 체크, 썸네일 재생성과 업로드, 검토 패널, PR 승인 패널 |
| `/schedules` | Google과 Naver 트렌드 키워드 조회 (주제 찾기용. 경로 이름과 달리 예약 기능은 없다) |
| `/analytics` | 일별 생성, 카테고리와 상태 분포, 최근 오류 |
| `/subscribers`, `/templates` | 뉴스레터 구독자와 이메일 템플릿 관리 |

**용어.** 화면에 쓰는 말을 그대로 따른다.

- 단위는 "작업"이다.
- 단계: 리서치, 초안 작성, AI 검토, 콘텐츠 개선, 정확도 검증, 썸네일, 검증, 사용자 검토, PR 생성.
- 상태: 대기중, 실행중, 리서치 중, 작성 중, AI 검토 중, 콘텐츠 개선 중, 썸네일 생성 중, 검증 중, 사용자 검토 대기, 보류 중, PR 승인 대기, PR 생성 중, 완료, 실패.
- 검토 액션: 승인, 수정 요청(최종본에 피드백 반영), 재작성(초안부터 다시), 보류.

**제약**

- 로그인이 없다. 한 사람이 쓰는 것을 전제로 한다.
- 주 사용 환경은 데스크톱이다. 모바일에서도 동작은 한다.
- 무료 티어라 LLM 호출 수가 곧 비용이다.

**미정. 지어내지 말 것.**

- 사용자 검토 대기는 30분이 지나면 자동 승인된다(`lib/workflow/executor.ts`). "돌려 놓고 나중에 검토"하는 실제 사용 방식과 부딪힌다. 어떻게 풀지 정하지 않았다.
- 면접관에게 라이브 데모를 할 때 `/subscribers`에 실제 구독자 이메일과 이름이 보인다. 가릴지, 데모용 데이터를 쓸지 정하지 않았다.
- 배포할지, 한다면 어디에 할지 정하지 않았다.

## Brand Commitments

- 이름은 "AI Agent", 설명은 "블로그 포스트 생성기"다 (기존 메타데이터).
- 글은 한국어로 쓴다. 번역투를 쓰지 않고, 한 문장에 한 가지만 담는다. 기술 용어와 코드 식별자는 원문 그대로 둔다.
- 사용자가 직접 정한 시각 제약 (2026-09-21). 구체적인 색과 서체는 이 문서가 아니라 디자인 문서의 몫이다.
  - 바깥 박스 테두리를 쓰지 않는다.
  - 아이콘을 쓰지 않는다.
  - 색상과 typography로 가시성을 확보한다.
  - 여백은 최소로, 텍스트는 작게 한다.
  - 헤더 아래 테두리를 두지 않는다.
  - 제목과 숫자를 포함해 모든 글자를 SUIT(https://sun.fo/suit/) 서체 하나로 통일한다.

## Evidence on Hand

- 운영 데이터 (2026-09-21 화면 기준): 작업 20건, 완료 17건, 실패 1건, 성공률 94%.
- 발행 실적: 블로그 105편 중 12편이 이 파이프라인으로 나갔다 (2026-01-19 ~ 02-13, `post/` 브랜치 머지 기준). 세는 방법은 `docs/ARCHITECTURE.md`에 있다.
- 설계 근거 문서: `docs/ARCHITECTURE.md`, 루트 `README.md`.
- 동작 증거: `apps/agent/tests/` 그래프 분기 테스트, GitHub Actions CI.

**없는 것.** 앞으로의 작업에서 만들어 내지 않는다.

- 검토에 걸린 시간과 반려율을 잰 값이 없다. 성공 기준 2번과 3번은 아직 숫자로 답할 수 없다.
- 외부 사용자, 후기, 사용량 수치가 없다.

## Product Principles

1. **애매하면 사람에게 넘긴다.** 자동화 범위를 넓히기보다 사람이 판단하기 쉽게 만드는 쪽을 택한다.
2. **돌아온 사람이 바로 이어서 일한다.** 자리를 비웠다 돌아오는 도구다. 어떤 작업이 내 결정을 기다리는지가 가장 먼저 보여야 한다.
3. **검토 시간을 줄이는 일이 기능 추가보다 먼저다.**
4. **처음 보는 사람에게도 읽힌다.** 면접관이 설명 없이 화면만 보고 파이프라인과 사람 개입 지점을 알아볼 수 있어야 한다.
5. **숫자는 실제 값만 쓴다.** 실적과 지표는 저장소와 DB에서 확인되는 값만 보여 준다.
